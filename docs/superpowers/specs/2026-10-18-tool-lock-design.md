# Tool lock file: pinned, verified tool installs

Date: 2026-10-18
Status: design, pending review
Roadmap: 2.0, item 5 (integrity of downloaded tools)

## Goal

Make every tool install reproducible and verified against a hash that was
recorded *before* the download, not one fetched next to it.

Today every GitHub tool tracks `latest`, so two machines (or one machine a week
apart) can run different binaries. Six tools are checked against the release's
own `checksums.txt` — that catches a corrupted download, but not a replaced
release, since the archive and its checksum come from the same place. RustScan
and gowitness (`needs_checksum: false`) are not checked at all, and the manual
`sha256:` map in `registry.yaml` is unused.

After this change `cyberfw init` installs exactly the release recorded in a
committed `tools.lock` and refuses any archive whose SHA-256 differs from the
lock. New upstream releases arrive only through an explicit
`cyberfw lock --upgrade`, which shows what changed.

Success: two machines (e.g. Windows and WSL) installing from one `tools.lock`
get byte-identical archives; a tampered or replaced archive fails the install
and leaves the previous install in place.

## Decisions (settled)

- **Pinning.** `init` installs the locked release; versions move only via
  `cyberfw lock --upgrade` (like `uv.lock` / `package-lock.json`).
- **Separate file.** `registry.yaml` stays the intent (which tools, from where,
  optional `version:` constraint); `tools.lock` is the resolved, verified state,
  written only by cyberfw.
- **All supported platforms.** One lock covers linux/amd64, linux/arm64,
  darwin/amd64, darwin/arm64, windows/amd64 and windows/arm64 (the README
  promises x64 and ARM64 on all three OSes), so a lock made on Windows works
  in WSL and on macOS. (windows/arm64 added after review — see the end.)
- **Hash source order at lock time:** GitHub API asset `digest` → the release's
  `checksums.txt` → download and hash locally. When both a digest and a
  checksums entry exist they must agree, or locking that tool fails.
- **`init` never rewrites an existing lock entry.** It only adds entries for
  tools missing from the lock. Changing a pin is `cyberfw lock`'s job.
- **Breaking (2.0):** `sha256:` and `needs_checksum:` leave `registry.yaml`.
  Every locked asset is always verified.

## The lock file

Location: next to the `registry.yaml` in use — `<registry dir>/tools.lock`. In
a checkout (or an editable install) that is the repo root, and the file is
committed. The wheel ships it as package data next to the packaged registry
(`cyberfw/data/tools.lock`), so a non-workspace install gets the release's
pins. A packaged lock is read-only: installing from it works; changing it
fails with a clear message (see Errors).

Format (YAML, written by cyberfw):

```yaml
# tools.lock — generated by `cyberfw lock`; do not edit by hand.
# Pins every downloaded tool to one release and the SHA-256 of each platform's
# asset. `cyberfw init` installs exactly these and refuses an archive whose hash
# differs. Change pins with `cyberfw lock [--upgrade] [tool ...]` and commit.
version: 1
tools:
  gowitness:
    repo: sensepost/gowitness
    tag: 3.2.2
    assets:
      linux/amd64:
        name: gowitness-3.2.2-linux-amd64
        url: https://github.com/sensepost/gowitness/releases/download/3.2.2/gowitness-3.2.2-linux-amd64
        sha256: 063ac21063ec…   # 64 lowercase hex
        source: digest          # digest | checksums | download
      # … one entry per supported platform the release has an asset for
```

- `version` is the file-format version (1); an unknown value is a read error.
- `url` is the asset's `browser_download_url` and must be `https://`, so an
  install from the lock needs no GitHub API call (and no rate limit).
- `source` records where the hash came from, for auditing.
- A platform with no matching asset in the release is simply absent.
- Output is deterministic: tools sorted by name, platforms in
  `SUPPORTED_PLATFORMS` order, fixed key order. Rewriting an unchanged lock is
  byte-identical, so git diffs show only real changes. Writes are atomic
  (temp file + `os.replace`).

## Resolving a lock entry

For one registry tool (`source: github`):

1. Fetch the release: the registry's `version:` tag when pinned, else `latest`.
2. For each platform in `SUPPORTED_PLATFORMS`, pick the asset with
   `select_asset(release, spec, mapping)` — the selection logic moved verbatim
   out of `ToolInstaller.install` into a pure function, so the lock and the
   installer can never disagree on which file a platform gets.
3. Hash each selected asset:
   - the asset's API `digest` (`sha256:<hex>`; any other algorithm counts as
     absent) and/or its line in `checksums.txt` (fetched once per release);
   - both present and different → `LockError` ("digest and checksums.txt
     disagree for <asset>"); one present → use it;
   - neither → download to a temp dir, hash, delete (`source: download`;
     currently only RustScan, whose latest release predates GitHub digests).

`source: local` tools (nmap) are never locked.

## Installing from the lock

`ToolManager.install(name, force=False)`:

1. Load the lock. If the tool has no entry, resolve it, add it and write the
   lock right away (one write per added tool, so `init` and `install` share a
   single code path).
2. Reject a stale entry (see Errors) — install never rewrites it.
3. Take the entry's asset for this machine's platform; none → error.
4. Up to date when the install state's `version` equals the locked version
   (the `tag` without a leading `v`, which is what the install state already
   records) **and** its recorded `sha256` equals the locked hash. A pre-lock
   (1.x) install has no recorded hash, so it is re-downloaded once and
   verified. `--force` always re-downloads.
5. `ToolInstaller.install_locked(spec, version, asset)`: download the locked
   URL, compare `sha256_hex` with the locked hash **before** touching the
   previous install (the existing ordering), then extract as today.
6. Write the install state with `sha256` added.

## `cyberfw lock`

```
cyberfw lock [TOOLS...] [--upgrade] [--token TOKEN]
```

- Plain `lock` makes the lock satisfy the registry with the fewest changes:
  add github tools missing from the lock, re-resolve stale entries, and drop
  entries for tools no longer in the registry (or now `local`). Entries that
  already satisfy the registry stay as they are.
- `--upgrade` also moves the named tools (default: all github tools) to the
  newest release the registry allows (`latest`, or its pinned `version:`).
- A re-resolved release whose **tag is unchanged** but where an already-locked
  platform's asset name or SHA-256 differs means upstream replaced a published
  file — exactly what the lock exists to catch. That tool is reported as
  failed and its old entry is kept; accepting the new file is deliberate
  (remove the tool's entry, then `cyberfw lock <tool>`). New platforms
  appearing under the same tag are fine ("updated").
- `TOOLS` restricts which tools are considered; dropping removed tools
  happens only when no `TOOLS` are given. An unknown name is a usage error
  (exit 2); a `local` tool named in `TOOLS` is skipped with a note.
- Prints a table: tool · before · now · change (added / upgraded /
  re-resolved / updated / removed / unchanged / failed) · hash sources.
  Writes only when something changed; otherwise prints "tools.lock
  unchanged".
- A tool that fails to resolve (network, rate limit, digest/checksums
  conflict) is reported; the others are still written; exit code 1.

`cyberfw init` with no `tools.lock` creates it first and prints a one-line
note to commit it. Hash mismatches appear as a failed row; exit code 1 as for
any failed install.

## Errors

| Situation | Behaviour |
|-----------|-----------|
| Downloaded archive's SHA-256 ≠ lock | `ChecksumError` "SHA-256 mismatch for <asset>: tools.lock has <x>, got <y>"; archive deleted, previous install untouched |
| Stale entry: lock `repo` ≠ registry `repo` | `LockError` "tools.lock is out of date for <tool>: repo changed (lock: A, registry: B) — run `cyberfw lock`" |
| Stale entry: registry pins `version:` ≠ locked tag | `LockError` "… registry pins vX, lock has vY — run `cyberfw lock`" |
| No locked asset for this platform | `DownloadError` "<tool> <tag> has no locked asset for <os/arch>" |
| Malformed lock (YAML, schema, bad hash/URL, unknown `version`) | `LockError` naming the file |
| Lock not writable (packaged copy) | `LockError` "cannot write <path> … run cyberfw from a workspace (a directory with registry.yaml) to change pins" |
| digest and checksums.txt disagree at lock time | `LockError`; that tool is not locked |

`LockError` is a new `CyberfwError` subclass in `exceptions.py`.

## Registry changes (2.0, breaking)

- `ToolSpec` loses `sha256` and `needs_checksum`. When a registry still has
  them, `load_registry` logs one warning per tool ("… no longer used —
  integrity now comes from tools.lock; run `cyberfw lock`") and ignores them.
- `version:` stays: it constrains what `lock` / `lock --upgrade` resolves.
- The bundled `registry.yaml` header comment and entries drop both fields.

## Testing (TDD)

All offline, with a fake `GitHubClient` (releases, digests, checksums text,
downloads).

- **Lock file:** write → read round-trip; rewriting an unchanged lock is
  byte-identical; bad hash / non-https URL / unknown format version / broken
  YAML → `LockError` naming the file; missing file → no lock.
- **Resolution:** digest used (`source: digest`); checksums used without a
  digest; both agreeing is fine; disagreeing → `LockError`; neither → asset
  downloaded and hashed (`source: download`); platforms without an asset
  omitted; a registry pin resolves that tag.
- **`select_asset`:** the existing installer asset-selection tests move here
  unchanged (macOS naming, OS-only fallback, the Windows catch-all).
- **Staleness:** repo change and pin mismatch are stale; `latest` with any tag
  is not.
- **Install:** matching hash installs; mismatch → `ChecksumError` with the
  previous install intact and no archive left; missing entry is added and the
  lock written; an existing entry is never modified by `install`; stale entry
  and missing platform asset error; up-to-date needs version **and** hash
  (a state without `sha256` reinstalls); `--force` re-downloads and verifies.
- **CLI:** `lock` creates the file; a second run prints "unchanged" and leaves
  it byte-identical; `lock --upgrade nuclei` changes only nuclei and shows
  before → now; a tool removed from the registry is dropped; a stale entry is
  re-resolved by plain `lock`; `init` without a lock creates it and says to
  commit it; a hash mismatch is a failed row and exit 1.
- **Registry:** legacy `sha256` / `needs_checksum` keys warn and are ignored.
- **GitHub client:** `digest` parsed (`sha256:<hex>` → hex; other algorithm or
  absent → `None`) and preserved through the release cache.
- Existing installer / manager / registry tests that relied on the removed
  fields are rewritten against the lock.
- Full suite, `ruff`, `mypy --strict`.

## Rollout

The repository's first `tools.lock` is generated by running `cyberfw lock`
against GitHub (8 release lookups, the published checksums files, and a
one-time download of RustScan's platform assets to hash them), then committed.
That step needs the network and downloads files, so it is run only with the
user's go-ahead. The `pyproject.toml` force-include of `tools.lock` lands in
the same step, after the file exists: hatchling fails the build on a missing
forced include, which would break `uv run` for every earlier task.

## Out of scope

- The portable Chromium for gowitness (Chrome for Testing publishes no hashes;
  hashing five platforms means ~750 MB at lock time).
- Signature / provenance verification (Sigstore, GitHub artifact
  attestations) — upstream tools do not sign consistently.
- Re-verifying installed binaries at rest (e.g. in `doctor`).
- `cyberfw lock --check` for CI.
- Platforms beyond the five above.

## Changes after the whole-branch review

- **windows/arm64** joins the supported platforms. Where a release has no
  native build, a platform gets the one it emulates: x64 on Windows on ARM,
  x86_64 under Rosetta on Apple silicon. Linux never falls back across
  architectures.
- **Architecture-aware selection.** `select_asset`'s registry-pattern fallback
  no longer uses patterns that name another architecture. Before, RustScan
  (arch-first names, aarch64 listed first) pinned `aarch64-linux-rustscan.zip`
  for linux/amd64 — a non-runnable binary for every x86_64 Linux / WSL user.
- **Selection fingerprint.** Each lock entry records `selection:` — a hash of
  the selection-rules version (`SELECTION_RULES`), the supported platforms and
  the tool's `asset_patterns`. A mismatch makes the entry stale: plain
  `cyberfw lock` re-resolves it, `init` asks for `cyberfw lock`. An entry
  without the field (locked before it existed) is stale.
- **Same-release check, split.** When a re-resolved entry keeps its repo and
  tag, a locked file that is still picked must keep its SHA-256 (else
  "changed upstream", entry kept) — even while the entry is stale. A platform
  getting a *different* file is refused only when nothing of ours changed
  (the entry is not stale); after a registry edit or a rules change it is an
  ordinary re-resolve, not a false tampering alarm.
- A lock that is not UTF-8 (Windows PowerShell 5.1 writes UTF-16 / cp1252) is a
  `LockError` naming the file; a just-hashed file that Windows Defender still
  holds no longer loses the hash or the whole lock run.
